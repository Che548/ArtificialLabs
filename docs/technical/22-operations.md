# Технический справочник эксплуатации

Команды ниже относятся к подготовленной локальной среде с доверенными исходниками. Конфигурация .env.local создаётся на основе .env.example и остаётся вне Git. EXPO_PUBLIC_CONVEX_URL нужен мобильному клиенту; CONVEX_SELF_HOSTED_URL и CONVEX_SELF_HOSTED_ADMIN_KEY нужны операторскому CLI. Публичный префикс переменной означает, что её значение может попасть в клиентский код.

| Команда | Результат |
| --- | --- |
| npm ci | Воспроизводимая установка корневых зависимостей |
| npm --prefix admin ci | Установка отдельного пакета консоли |
| npm run start | Запуск среды Expo |
| npm run ios или npm run android | Сборка и запуск нативного приложения |
| npx convex codegen | Генерация локальных серверных привязок |
| npm run verify | Общий агрегат проверок проекта |
| npm --prefix admin run verify | TypeScript и статическая сборка консоли |

Развёртывание функций выполняет npx convex dev --once --env-file .env.local. Эта команда изменяет серверную среду, а не только генерирует локальные типы. Её использование должно относиться к подготовленному выпуску. Для первоначального назначения администратора применяется npx convex run admin:bootstrapByEmail с явным JSON-аргументом email и тем же env-file; реквизиты аккаунта не включаются в документацию.

Нативные изменения проверяются собственным бинарником. Совместимость Expo контролируется npm run check:expo и npm run doctor; типы приложения и Convex — отдельными typecheck-командами. После изменения административной части требуется сборка её статического экспорта, поскольку успешный корневой TypeScript не равнозначен проверке admin/.

Для ИИ нужно различать точные значения флагов: AI_AGENT_ENABLED=true, AI_AGENT_AUTOMATION_ENABLED=true, AI_DOCUMENT_OCR_ENABLED=1 и AI_DOCUMENT_INTERPRETATION_ENABLED=1. Это справочник синтаксиса, а не указание включить функции. Разрешения пользователя и условия допуска остаются обязательными.

SMS_AUTH_ENABLED=1 допускает SMS-доставку. SMS_LOGIN_ENABLED=1 является самостоятельным временным разрешением входа только по коду. EMAIL_VERIFICATION_REQUIRED=1 включает проверку email; переходный режим legacy должен рассматриваться отдельно. RESEND_API_KEY, PASSWORD_RECOVERY_HASH_SECRET и секреты шлюза относятся исключительно к серверу.

При передаче выпуска фиксируются commit, нативный build, runtimeVersion и update ID каждой платформы. При публикации веба фиксируется тег или digest контейнера. Канал latest либо production является изменяемым указателем; для воспроизводимого разбора инцидента нужен идентификатор самого артефакта.

## Разделение конфигурации по моменту применения

У конфигурации три разных момента применения. Публичные EXPO_PUBLIC_* и NEXT_PUBLIC_* участвуют в сборке клиентского артефакта. Серверные ключи, модели и feature flags читаются функциями Convex в окружении развёртывания. Порты, тома и пути секретов относятся к контейнерному запуску. Для изменения параметра сначала определяют этот уровень, затем выбирают пересборку, изменение серверного окружения или пересоздание службы; единого «перезапуска проекта» для всех трёх уровней нет.

EXPO_PUBLIC_CONVEX_URL и NEXT_PUBLIC_CONVEX_URL обязательны для соответствующих клиентов: отсутствие адреса приводит к явной ошибке инициализации. Нативный E2E-режим может выбирать платформенный адрес только при EXPO_PUBLIC_E2E_MODE=1; это отдельная конфигурация проверок. Пакет передачи выпуска должен фиксировать публичные адреса, точные идентификаторы артефактов и перечень изменённых серверных параметров, сохраняя значения секретов в предназначенном для них окружении.

## Выбор действия после прерванной интеграционной операции

Порядок восстановления определяется наличием подтверждённого побочного эффекта. Для синхронизации таким свидетельством служит точное подтверждение отправленной версии outbox; неподтверждённая запись остаётся ожидающей. Для обработки документа сохранённый nextRequestId означает, что запрос мог уже достичь поставщика: при прерывании recognizing преобразуется в ошибку OCR_UNCERTAIN, требующую явного решения о повторе. Если идентификатор ещё не сохранён, задание может вернуться в queued. Универсальный повтор любого сетевого исключения нарушил бы это различие.

Регистрация Expo Push использует иной порядок: локальное разрешение и настройка сохраняются независимо от успешной регистрации серверного канала. При отказе регистрации интерфейс сообщает о локальном режиме, а новая попытка предусмотрена при следующем авторизованном запуске. Ошибка пересчёта локального расписания также не отменяет сохранённые предпочтения. При проверке восстановления следует наблюдать фактическое расписание и состояние удалённого канала раздельно, а не считать успешное изменение переключателя доказательством обоих результатов.

Для выпуска единицами подтверждения являются образ и его digest, развёрнутые функции, а также отдельные update ID платформ и указатели каналов. После частичного сбоя сначала фиксируется фактически достигнутое состояние каждого компонента, затем повторяется нужный этап. Такой порядок связывает восстановление с конкретным ресурсом и позволяет отличить безопасный повтор чтения, повтор идемпотентной записи и новую операцию с внешним побочным эффектом.

## Конфигурация по месту и моменту применения

Публичные параметры встраиваются в JavaScript при сборке. Серверные секреты задаются в окружении Convex; контейнерные параметры читаются при запуске службы. Изменение переменной в запущенном nginx не меняет URL, уже встроенный в статический экспорт.

| Параметр | Область | Назначение |
| --- | --- | --- |
| `EXPO_PUBLIC_CONVEX_URL` | Сборка Expo | Клиентский backend |
| `EXPO_PUBLIC_CONVEX_SITE_URL` | Сборка Expo | HTTPS HTTP actions, включая документы |
| `NEXT_PUBLIC_CONVEX_URL` | Сборка admin | Backend статического клиента |
| `CONVEX_SELF_HOSTED_URL` | CLI и защищённый CI | Целевое развёртывание |
| `CONVEX_SELF_HOSTED_ADMIN_KEY` | Секрет CLI или CI | Привилегированное развёртывание |
| `JWT_PRIVATE_KEY`, `JWKS` | Convex Auth | Закрытый ключ подписи и конфигурация проверки токенов |
| `YANDEX_AI_API_KEY`, `YANDEX_AI_FOLDER_ID`, `YANDEX_AI_MODEL` | Convex | Реквизит и параметры поставщика |
| `RESEND_API_KEY`, `RESEND_FROM`, `PASSWORD_RECOVERY_HASH_SECRET` | Convex | Почта и защита восстановления |
| `SMS_GATEWAY_SHARED_SECRET`, `SMS_RATE_LIMIT_HASH_SECRET` | Приватный шлюз и Convex | Аутентификация доставки и HMAC-лимиты |
| `ANALYTICS_HASH_SECRET` | Convex | Псевдонимизация дневной активности |
| `OTA_PUBLISH_SECRET`, `OTA_SIGNING_PRIVATE_KEY_PATH` | Служба OTA | Управляющая аутентификация и путь к ключу подписи |

`JWT_PRIVATE_KEY` является закрытым ключом. `JWKS` описывает ключи проверки подписи; его конфигурация не должна содержать приватный материал. Правила проекта предписывают хранить обе настройки в серверном окружении, а не в клиентской конфигурации. Значения секретов не приводятся ни в документации, ни в журналах команд.

| Флаг | Значение включения | Дополнительное условие |
| --- | --- | --- |
| `AI_AGENT_ENABLED` | `true` | Настроенный поставщик и согласие |
| `AI_AGENT_AUTOMATION_ENABLED` | `true` | Основной флаг агента и разрешение автоматизации |
| `AI_DOCUMENT_OCR_ENABLED` | `1` | Облачный режим и отдельное согласие |
| `AI_DOCUMENT_INTERPRETATION_ENABLED` | `1` | Выбор текста и отдельное согласие |
| `SMS_AUTH_ENABLED` | `1` | Доступный приватный шлюз |
| `SMS_LOGIN_ENABLED` | `1` | Временный режим входа только по коду |
| `EMAIL_VERIFICATION_REQUIRED` | `1` | Совместимые клиенты и проверенные review-аккаунты |
| `EXPO_PUBLIC_E2E_MODE` | `1` | Только контролируемая проверочная сборка |

Шаблон `.env.example` копируется в игнорируемый `.env.local`. Реальные значения не включаются в Git. Порты и origins Convex задаются в `infra/convex`, веб-образ — через `WEB_IMAGE`, параметры OTA — в приватном окружении `infra/updates`. Фактическое включение флага на рабочем сервере не выводится из значения в примере. При изменении Android package или подписи пересчитывается SMS Retriever hash. Эффективную конфигурацию определяет `app.config.ts`, который переопределяет `app.json`: базовый iOS bundle — `com.anonymous.privateexpo`, а при `SFERA_IOS_APP_STORE=1` используются `engineering.brainwaves.sfera`, Team ID `6HZGXYF43L` и buildNumber `5`. Совмещение этого флага с E2E-режимом отклоняется. Android package — `engineering.brainwaves.sfera`, versionCode — `6`. Для выбранного профиля выпуска проверяются сертификат подписи, entitlement Associated Domains, AASA и SMS-формат; значения базового профиля нельзя механически переносить в магазинную сборку.

Политика OTA задаёт `checkAutomatically: ON_ERROR_RECOVERY` и `fallbackToCacheTimeout: 0`. Это не обещание автоматического получения нового пакета при каждом холодном запуске. Канал по умолчанию — production; runtime вычисляется по fingerprint. Исключения E2E для локального URL и сертификата не описывают штатную конфигурацию выпуска.

## Подготовка локальной среды и воспроизводимая установка

Исходный состав задаётся `package.json`, корневым `package-lock.json`, отдельным lock-файлом `admin/` и нативной конфигурацией. В корне требуется Node не ниже 20.19.4; для воспроизведения CI следует использовать версию из `.nvmrc`. Не следует смешивать изменение зависимостей с запуском уже зафиксированного состава.

```sh
npm ci
npm --prefix admin ci
cp .env.example .env.local
npm run start
```

После заполнения публичного URL Expo подключается к выбранному backend. Привилегированный ключ требуется CLI, но не приложению. Команда `npm run convex:codegen` генерирует привязки; `npm run convex:deploy` выполняет реальное развёртывание функций в указанное окружение. Это разные по последствиям действия.

```sh
npm run check:expo
npm run typecheck
npm run typecheck:convex
npm --prefix admin run verify
```

Нативное приложение запускается через `npm run ios` или `npm run android`. SQLCipher, собственные модули, плагины защиты данных и SceneDelegate требуют development/release-сборки. Expo Go не подтверждает наличие этих возможностей. Генерируемые платформенные каталоги изменяются через конфигурацию и плагины; после prebuild проверяется, что требуемые изменения воспроизводятся.

`npm run build:expo-web` создаёт демонстрационный экспорт Expo. `npm run build:web` собирает защищённую административную часть. Проверка одного экспорта не подтверждает другой. Для редактирования статей есть локальный `npm run preview:admin-ui`; этот стенд использует искусственные данные и не является рабочей административной средой.

## Матрица проверок и границы доказательств

Проверка связывается с точным состоянием исходников, конфигурацией и артефактом. Результат из протокола за другую дату не подтверждает новую рабочую копию. Тест с подменённым поставщиком проверяет обработку контракта, но не фактическую доставку или поведение нативной библиотеки.

| Команда | Проверяемая область |
| --- | --- |
| `npm run test:document-policy` | Форматы документов, задачи, согласия и серверный транспорт |
| `npm run test:document-ui` | Локальные браузерные сценарии проверки документа |
| `npm run test:chat-feedback` | Состояния чата, согласия, соединение и компоновка |
| `npm run test:chat-feedback:web` | Браузерные проверки интерфейса чата |
| `npm run test:contacts` | Подтверждение контактов и восстановление |
| `npm run test:contacts:ui` | Интерфейс контактов на искусственных данных |
| `npm run test:today-content` | Markdown и публикация статей |
| `npm run test:admin` | Полномочия, каталог аккаунтов, агрегаты и CMS |
| `npm run test:admin-ui` | Интерфейс административной части |
| `npm run test:ios-config` | Плагины iOS, защита хранения и SceneDelegate |
| `npm run test:android-config` | Нативная конфигурация Android |
| `npm run ota:test` | Хранилище и протокол обновлений |
| `npm run verify` | Предметные проверки, типы, Expo и сборки |

`npm test` и `npm run verify` имеют разный состав; перед изменением проверяется действующий список scripts. Публичный CI получает только публичную конфигурацию. Живые backend-проверки используют отдельные одноразовые аккаунты с точной очисткой; `e2e-live.yml` запускается вручную. Нативная проверка использует Maestro и приватные временные файлы в игнорируемых каталогах. Реальные SMS, USSD и пользовательские документы не относятся к регулярным CI-проверкам.

Минимальные отрицательные сценарии: отказ другому владельцу; отсутствие или отзыв согласия; смена аккаунта во время запроса; потеря ответа после серверной записи; изменение строки до ACK; неподдерживаемая версия; восстановление после остановки приложения; конфликт редактирования; несовпадение runtime OTA. Проверка локального сохранения должна завершиться успешно при временном сетевом отказе. Ошибка Auth не должна запускать бесконечный транспортный повтор.

## Разбор инцидента и безопасная передача контекста

В обращении достаточно версии приложения, build, commit, update ID, платформы и версии ОС, времени и последовательности действий, безопасного кода ошибки и результата повторного открытия. Указываются наличие связи, выбранный режим синхронизации и стадия операции. Не прикладываются медицинские значения, тексты документов и чатов, локальные пути, номера телефонов, токены, ключи или необработанные исключения.

Для ошибки локальной записи сначала проверяется доступность защищённого хранилища. Для синхронизации различаются транспорт, Auth, отсутствие профиля и отказ валидации. Для обработки документа различаются импорт, рендеринг, резервация, неопределённый исход отправки и проверка ответа. Для уведомлений проверяются разрешение ОС, локальное расписание и регистрация удалённого канала. Для OTA проверяются платформа, runtime, канал, подпись и соответствие ресурсов.

Сигнал о возможной потере данных, применении ответа к другому владельцу, обходе отзыва или раскрытии секрета требует немедленной передачи ответственному за соответствующую подсистему. Временное ограничение функции должно сохранять локальные данные. Закрытие инцидента требует воспроизведения причины на безопасных данных, проверки исправления и подтверждения нужного артефакта; исчезновение одного сообщения об ошибке не доказывает исправление причины.
