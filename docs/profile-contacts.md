# Контакты профиля

Телефон добавляется через модальное окно и существующий Convex Phone provider.
Подтверждённый номер по-прежнему используется с паролем; OTP-вход не включается.
Смена подтверждённого номера требует текущий пароль и SMS на новый номер.
Подтверждение email для регистрации и следующего входа существующих пользователей
реализовано за серверным флагом `EMAIL_VERIFICATION_REQUIRED=1`. При выключенном
флаге сохраняется прежний вход; действующие сессии массово не отзываются.

## Подтверждение входа

Временный режим перехода: `EMAIL_VERIFICATION_REQUIRED=1` вместе с
`EMAIL_VERIFICATION_ALLOW_LEGACY=1`. Новые клиенты уже отправляют
`emailTicketToken` и обязаны подтвердить неподтверждённый email. Старые запросы,
в которых параметр отсутствует, допускаются после правильного пароля. Пустой
или повреждённый параметр не считается старым клиентом. Это не надёжное
определение версии: прямой API может имитировать старый клиент, опустив параметр.
Для окончательного закрытия обхода установить `EMAIL_VERIFICATION_ALLOW_LEGACY=0`
(или удалить переменную), сохранив `EMAIL_VERIFICATION_REQUIRED=1`. Тогда старым
неподтверждённым пользователям требуется обновление клиента. Исключения двух
ревьюеров продолжают действовать; текущие сессии не отзываются.

Password и phone-password сначала проверяют настоящий пароль. Если email не
подтверждён, вместо сессии возвращается запрос подтверждения. Клиент держит
случайный 256-битный токен запроса только в памяти, сервер — его HMAC. Завершение
через password / email-verification требует токен и шестизначный код. Восстановление
пароля не выдаёт сессию в обход этой проверки. Старый клиент при включённом флаге
получит требование обновления, поэтому раннее включение недопустимо.

Код живёт 10 минут, повторная отправка через 60 секунд не продлевает запрос и не
сбрасывает пять допустимых ошибок. Лимиты отправки: пять за 24 часа отдельно по
пользователю, адресу и HMAC IP. Resend использует существующий учёт квот.

## Смена телефона

`phoneChange.request({newPhone,currentPassword,platform})`, `resend({challengeId})`
и `confirm({challengeId,code})` требуют текущую активную сессию. Код живёт пять
минут; авторизация смены паролем — максимум час. Повторная отправка аннулирует
прежний код, но сохраняет счётчик ошибок. Шлюз сохраняет существующие ограничения
по номеру/IP и интервалы 5/30 минут; добавлен лимит три отправки за сутки по
пользователю. Формат SMS и автозаполнение платформ не меняются.

Атомарно заменяются подтверждённый телефон и его auth-идентификатор, отменяются
незавершённые восстановления старого номера и остальные сессии. Текущая сессия,
пароль, userId и медицинские данные сохраняются. Повторное подтверждение безопасно.

## Доступ ревьюеров

`reviewAccess.configure` — только internalMutation для операторского CLI.
Точные userId и текущий email должны быть сверены с App Store Connect и Play
Console; нужны два разных существующих обычных аккаунта без реальных медицинских
данных. Нельзя подставлять предполагаемые адреса. Администраторы исключены.
Оператор передаёт store, active, consoleAccountVerified и краткую причину без
секретов. Выдача/отзыв фиксируются в reviewLoginAudit. Смена email отзывает
исключение. Оно не отменяет пароль, SMS, подтверждение нового email или recovery.

После фактической настройки добавить в инструкции обеих консолей:
"Use the provided email and password to sign in. This prepared, non-administrator
review account does not require an additional email verification code at login.
All application features are the same as for other users. Changing contacts
requires normal verification. No real medical data is included."
Пароли и конкретные учётные данные хранятся вне Git. До проверки и настройки
исключений этот текст нельзя публиковать как описание уже работающего доступа.

Смена email: `emailChange.request({newEmail,currentPassword})`,
`resend({challengeId})`, `confirm({challengeId,code})`. Сервер требует активную
сессию; код привязан к ней и текущему password-аккаунту. Запрос живёт 10 минут,
включая повторные отправки; после истечения нужен пароль заново. Пять отправок
за 24 часа отдельно по пользователю, адресу и IP, интервал 60 секунд. Пять
неверных кодов блокируют запрос; resend не сбрасывает счётчик. Проверка пароля
дополнительно ограничена пятью запросами за час по пользователю/IP.

Используются существующие `RESEND_API_KEY`, `RESEND_FROM` и
`PASSWORD_RECOVERY_HASH_SECRET` (HMAC с отдельным префиксом). Новые секреты
не нужны. Пароль/OTP не сохраняются клиентом; код и отпечаток credentials в
серверном запросе представлены HMAC. Email в ограниченной TTL-таблице необходим
для доставки и смены идентификатора. Таблицы не доступны публичными запросами.

Смена `users.email`, `authAccounts.providerAccountId`, флагов подтверждения,
погашение кода, отмена recovery и отзыв остальных сессий атомарны. Текущая
сессия и userId сохраняются. Уже выданные access JWT могут жить до истечения
срока согласно Convex Auth; refresh-токены остальных сессий удаляются сразу.
Уведомление старому адресу запускается после commit, не откатывает смену при
ошибке доставки. Медицинские записи и opt-in синхронизации не меняются.

## Проверки

- `npm run test:contacts`: изолированный Convex-test, доставка замокана.
- `npm run test:contacts:ui`: настоящий компонент через React Native Web,
  стенд только localhost, mock действий. Это не нативная проверка клавиатуры.
- `.maestro/profile-contacts.yml`: нативная проверка открытия/закрытия и
  клавиатуры с авторизованным одноразовым аккаунтом на экране Профиля. Форма
  отправки намеренно не нажимается: реальные SMS в автоматических тестах запрещены.
  Flow подключён к `product-surface.yml` для обоих устройств.
- Полная смена email на устройстве проверяется только с контролируемыми
  реальными ящиками после развёртывания backend, без публикации credentials.

Локально пройдены 37 серверных тестов контактов/восстановления и шесть UI-тестов
на трёх размерах экрана. Нативные E2E новой реализации не запускались: в этом
worktree нет совместимых нативных сборок, Android-устройство не подключено.
Запущенные store-симуляторы содержат прежний клиент. Старый runner
сбрасывает Keychain симулятора, поэтому его нельзя запускать на пользовательском
симуляторе без подготовки изолированного тестового окружения.

## Порядок выпуска

1. Развернуть проверенный backend с `EMAIL_VERIFICATION_REQUIRED` выключенным.
2. Выпустить совместимый клиент в тестовый канал и проверить native E2E, включая
   настоящий login handshake и controlled-mailbox доставку. Автоматические SMS
   проверки работают только с подменой; живой модем проверяется вручную.
3. Сверить и настроить оба review-аккаунта, проверить правильный/неправильный
   пароль и отсутствие обхода смены контактов; обновить инструкции консолей.
4. Только после проверки выпускаемой сборки включить флаг на сервере.

Миграция данных и массовый отзыв сессий не нужны. Production и автоматизация
main → Preview — отдельная задача. При проблемах включения вернуть флаг в 0;
подтверждённые контакты не откатывать и данные пользователя не удалять.
