# Форматы импорта и экспорта

Документ определяет фактический контракт JSON и CSV, границу очистки локальных полей, порядок применения и известные ограничения. Эти файлы предназначены для переноса поддерживаемых структурированных записей, а не для полного восстановления приложения.

> [!summary] Главное ограничение
> JSON имеет строгую версию `1`, но проверяет предметную структуру большинства сущностей только частично. CSV не имеет версии. Импорт применяется по одной записи и не является атомарным для всего файла. Файл из недоверенного источника нельзя считать безопасным только потому, что предварительный просмотр показал количество записей.

## JSON-архив

Внешняя оболочка имеет вид:

```json
{
  "schema": "artificiallabs-health-archive",
  "version": 1,
  "exportedAt": 0,
  "profile": {},
  "entities": {}
}
```

`DATA_ARCHIVE_VERSION` равна `1`. Читатель требует точные `schema` и `version`; неизвестная, отсутствующая или будущая версия отклоняется как `UNSUPPORTED_ARCHIVE` до применения записей.

### Что входит

JSON может содержать:

- профиль;
- программы;
- дневник;
- лабораторные результаты;
- результаты сканирования;
- напоминания;
- медицинские состояния;
- препараты;
- риски аллергии;
- документы;
- беседы и сообщения;
- пользовательские настройки.

### Что не входит

Архив не содержит содержимое исходных файлов, изображения сканирования, вложения чата, локальные URI, учётные реквизиты, токены, серверные согласия, телеметрию, административные данные, план помощника, автономные правила и события рекомендаций.

Следовательно, JSON не является резервной копией SQLCipher-файла, SecureStore, Convex или всей учётной записи. После импорта карточка документа может сохраниться без самого документа, а вложение — без локального файла.

## Очистка переносимых данных

Перед сериализацией `portableValue()` рекурсивно удаляет ключи:

- `localImageUri`;
- `localDocumentUri`;
- `localFileUri`;
- `localUri`.

`availableLocally` принудительно становится `false`. Очистка выполняется для элементов `entities`; исходные файлы в архив не читаются.

При добавлении нового поля локального пути нельзя полагаться на его название. Нужно одновременно:

1. добавить его в очистку;
2. добавить корректный тестовый образец экспорта;
3. добавить отрицательный поиск URI во всём архиве;
4. проверить вложенные массивы и объекты;
5. обновить карту данных и пользовательское объяснение.

## CSV

Точный заголовок:

```text
entity,localId,updatedAt,deletedAt,payload
```

Все ячейки заключаются в двойные кавычки, а внутренняя кавычка удваивается. Парсер поддерживает запятые и переносы строк внутри кавычек и отклоняет незакрытую кавычку. В `payload` находится JSON без `localId`, `updatedAt` и `deletedAt`; эти значения берутся из отдельных столбцов.

Интерфейс предлагает CSV для дневника, анализов, сканов, медицинской истории, препаратов и аллергий. Сам генератор типизирован шире, но пользовательская поверхность не обещает экспорт каждой сущности.

CSV не содержит номера версии, кодировки или декларации предметной схемы. Любое изменение заголовка является несовместимым. Кавычки не нейтрализуют формулу для Excel-подобного редактора: значение, начинающееся с `=`, `+`, `-` или `@`, экспортёр не экранирует специальным префиксом. Файл не следует открывать в табличном редакторе из недоверенного источника без дополнительной защиты.

## Предварительный разбор

### Общий минимум записи

Для каждой записи проверяется:

- значение является объектом;
- `localId` — непустая строка;
- `updatedAt` — конечное число;
- сериализованный объект не содержит ключа, похожего на `localUri`, `localImageUri`, `localDocumentUri` или `localFileUri`.

Для JSON массив каждой известной сущности должен действительно быть массивом. Неизвестные ключи внутри `entities` игнорируются, потому что читатель перебирает только фиксированный список поддерживаемых сущностей.

Для профиля проверяются только строковый `displayName` и числовой `updatedAt`. Для большинства сущностей полная форма, перечисления, диапазоны, число элементов и `deletedAt` не валидируются на этапе разбора. В CSV `deletedAt` преобразуется через `Number`, но конечность результата отдельно не проверяется.

Название интерфейса «Проверено записей» означает успешный ограниченный разбор, а не полную проверку медицинского смысла или безопасности файла.

### Адаптер старого дневника

Внутри версии 1 поддерживается старая форма:

- `entryDate` становится `occurredAt`;
- непустой массив `symptoms` задаёт `kind: symptom` и формирует подпись;
- `notes` становятся `textValue`;
- при отсутствии типа используется `note`;
- при отсутствии источника используется `manual`.

Дата должна быть конечным числом, тип — одним из разрешённых видов дневника, источник — `manual`, `scan` или `lab`. После преобразования старые поля удаляются.

Это точечная совместимость, а не разрешение незаметно менять формат версии 1. Новая несовместимая форма требует новой версии и отдельного адаптера.

## Ограничения ресурса

`parseImportPayload()` не устанавливает собственный предел размера файла, числа записей, длины строки, глубины JSON или суммарной полезной нагрузки. Файл сначала целиком читается в строку, а затем разбирается в памяти.

До использования импорта для внешнего обмена необходимы ограничения на уровне выбора файла и парсера, а также испытания чрезмерного JSON, глубокой вложенности, больших массивов, очень длинных CSV-ячеек и повреждённой кодировки. Текущий test-файл этих сценариев не содержит.

## Применение

После подтверждения `health-store.importData()`:

1. обновляет профиль, только если его `updatedAt` не старше локального;
2. проходит сущности и записи последовательно;
3. вызывает `saveLocalRecord()` для каждой записи;
4. обновляет снимок интерфейса после завершения.

Одна запись сохраняется SQL-транзакционно. Ключом является `(entity, localId)`, а обновление выполняется, если импортный `updatedAt` больше или равен текущему. Повтор того же файла приводит к тем же значениям, однако две разные полезные нагрузки с одинаковым `updatedAt` разрешаются порядком применения, а не детерминированным сравнением содержимого.

Общей транзакции вокруг всего импорта нет. Если запись в середине вызывает ошибку, ранее записанные элементы остаются, последующие не применяются, а интерфейс не формирует отчёт по частичному результату. До исправления большой импорт следует выполнять только после отдельного экспорта текущих данных и с готовностью повторить идемпотентную часть.

Импортированные записи проходят обычную исходящую очередь. Наличие записи в очереди не означает разрешение на отправку: фактический обмен по-прежнему ограничивает политика облачной синхронизации. Для чатов постановка в очередь зависит от действующего облачного доступа в момент импорта.

## Модель доверия

Импорт является входом из внешнего файла и должен считаться недоверенным. Парсер не проверяет электронную подпись, автора, происхождение, хеш, антивирусный статус или соответствие учётной записи.

Файл нельзя применять автоматически после выбора. Предварительный просмотр обязан показывать формат, версию, категории и количества, а при будущем усилении — размер, предупреждения, конфликтующие записи и ожидаемое число замен. Медицинский текст не выводится в технический журнал.

## Экспорт и владение файлом

Экспорт создаётся во временном каталоге приложения и передаётся через системное меню. После передачи копия живёт по правилам выбранного пользователем приложения или места хранения. Удаление записи, очистка устройства или удаление учётной записи не уничтожают ранее сохранённый экспорт.

Архив содержит медицинские сведения в открытом JSON/CSV и не шифруется приложением. Пользовательская инструкция должна рекомендовать защищённое место и удаление лишних копий без обещания автоматического стирания.

## Воспроизводимые проверки

`lib/data-transfer.test.ts` подтверждает только:

- удаление локального URI документа из JSON;
- круговой проход одной CSV-записи с кавычками и переносом строки;
- отказ JSON неизвестной версии;
- нормализацию старого дневника;
- отказ дневника без пригодной даты.

Нативные сценарии ссылаются на импорт и экспорт в матрице покрытия, но отдельного поиска `parseImportPayload` в E2E-скриптах HEAD нет. Поэтому нельзя утверждать, что автоматически проверяются размер, формулы, дубли, частичное применение, все сущности, повреждённый профиль или неизвестные поля.

Минимальная локальная проверка:

```bash
npm test
npm run e2e:coverage
npm run verify
```

Для изменения формата требуются тестовые образцы предыдущей, текущей, повреждённой и неизвестной будущей версии, а также испытание реального выбора и применения файла в нативном приложении.
