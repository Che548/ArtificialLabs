# Зависимости и состав компонентов

Страница описывает источники версий, воспроизводимую установку, проверку обновлений и требования к перечню программных компонентов (SBOM).

> [!summary] Текущее состояние
> Версии JavaScript-пакетов закреплены файлами `package-lock.json`, а версия Node.js — файлом `.nvmrc`. CI устанавливает пакеты через `npm ci`. Автоматического формирования SBOM, обязательной проверки лицензий и уязвимостей и полного закрепления внешних действий и образов по неизменяемым идентификаторам пока нет.

## Источники точных версий

| Область | Манифест | Источник точной версии | Воспроизводимая проверка |
|---|---|---|---|
| Expo и React Native | `package.json` | `package-lock.json`, `.nvmrc` | `npm ci`, `npm run verify` |
| Административная консоль | `admin/package.json` | `admin/package-lock.json` | `npm --prefix admin ci`, `npm --prefix admin run verify` |
| Совместимость Expo SDK 54 | ограничения в `package.json` | `package-lock.json` и проверка Expo | `npm run check:expo` |
| Нативный StripCV | podspec, Gradle и CMake | версии в отслеживаемых файлах сборки | сборка, CTest и проверка запуска |
| Самоуправляемый Convex | `infra/convex/.env.example` | дайджесты образов серверной части и панели | проверка состояния Docker Compose |
| Веб-образ | `Dockerfile` | теги Node.js и nginx | сборка Docker и проверка `/health` |
| Развёртывание веб-образа | `infra/web/docker-compose.yml` | образ GHCR и Watchtower с тегом `latest` | состояние контейнера и `/health` |
| GitHub Actions | `.github/workflows/*.yml` | теги основных версий действий | выполнение задания GitHub Actions |

Диапазон в `package.json` не показывает фактически установленную версию. Для JavaScript-пакетов точным источником служит соответствующий lock-файл. Полное дерево формируется инструментом для конкретного коммита, а не копируется в документацию вручную.

На коммите `80c41c1` CI использует Node.js `22.13.1` из `.nvmrc`. Поле `engines` допускает версии от `20.19.4`, поэтому пакет выпуска должен указывать фактическую версию среды.

## Воспроизводимая установка

```bash
npm ci
npm --prefix admin ci
npm run verify
```

Lock-файл меняют только вместе с осознанным изменением манифеста или после штатной перегенерации выбранным менеджером пакетов. Ручное редактирование разрешённых версий внутри lock-файла запрещено.

Если `npm ci` меняет рабочее дерево, требует незафиксированного файла или даёт разные версии на одинаковой платформе, сборку нельзя считать воспроизводимой.

## Оценка обновления

| Риск | Примеры | Обязательная проверка |
|---|---|---|
| Низкий | типы и инструмент разработки без влияния на рабочий код | чистая установка, модульные испытания, `npm run verify` |
| Средний | библиотека интерфейса, клиент Convex, исправление Expo, пакет административной консоли | испытания затронутой области, Expo Doctor, обе веб-сборки |
| Высокий | основная версия Expo, React Native или Next.js; Auth; криптография; SQLCipher; камера; уведомления | пересмотр угроз, чистая нативная сборка, сквозные испытания, проверка возврата |
| Критический | эксплуатируемая уязвимость в аутентификации, подписи или хранилище | ограничение выпуска, срочное обновление, целевые регрессионные испытания, отдельное решение о выпуске |

Правила SemVer дают предварительную оценку, но не подтверждают совместимость. Транзитивный пакет может изменить нативную библиотеку, аутентификацию или сборку без изменения прямой зависимости.

## Требования к SBOM

Для каждого выпуска перечень компонентов должен содержать:

- имя, версию и устойчивый идентификатор компонента;
- признак прямой или транзитивной зависимости;
- контрольную сумму или дайджест доступного артефакта;
- лицензию и источник;
- связь с коммитом, платформой и дайджестом итогового образа;
- название и версию средства формирования;
- дату и время формирования.

Допустимы форматы CycloneDX и SPDX. В SBOM не включают `.env`, токены, локальные пути к медицинским материалам и рабочие данные. Перечень входит в закрытый пакет выпуска, но не в публичный веб-образ.

## Уязвимости и лицензии

До рабочего выпуска команда должна:

1. проверить дерево корневого приложения и `admin/`;
2. проверить контейнерный образ по неизменяемому дайджесту;
3. оценить применимость каждой находки высокой и критической опасности;
4. выявить запрещённые или несовместимые лицензии;
5. назначить владельца, срок и компенсирующую меру для принятого исключения;
6. повторить проверку после изменения любого lock-файла.

Текущие задания CI не делают эти проверки обязательным условием выпуска. Локальный `npm audit` не заменяет отчёт по контейнеру, анализ применимости и оформленное решение по исключению.

## Неизменяемые ссылки и происхождение

Образы серверной части и панели Convex задаются дайджестами в `infra/convex/.env.example`. Остальная цепочка поставки закреплена не полностью:

- действия GitHub указаны тегами основных версий, а не полными SHA;
- базовые образы Node.js и nginx указаны тегами;
- Watchtower и веб-развёртывание используют изменяемый `latest`;
- автоматизация не публикует подписанное подтверждение происхождения образа;
- загрузка рабочего образа не проверяет его подпись.

Это известные пробелы. Документация не описывает их как уже внедрённые меры защиты.

## Оформление изменения зависимости

Запись об изменении содержит:

1. причину и источник сведений об обновлении;
2. прежнюю и новую версии;
3. затронутые платформы, форматы данных и API;
4. изменения манифеста и lock-файла;
5. результаты испытаний, проверки уязвимостей и лицензий;
6. различие между прежним и новым SBOM;
7. версию или артефакт для безопасного возврата.

Изменение нельзя выпускать, если lock-файл обновился без объяснимого изменения состава, критическая находка не разобрана или способ возврата зависит от недоступного изменяемого тега.
