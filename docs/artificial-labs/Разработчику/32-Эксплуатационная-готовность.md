# Эксплуатационная готовность

## Службы инфраструктуры и защита эксплуатационного доступа

Проект использует выделенное self-hosted развёртывание Convex на узле junk. Клиентский backend, HTTP actions и dashboard опубликованы разными адресами. Приложению нужен публичный адрес Convex; CLI дополнительно использует административный адрес и ключ из защищённого окружения. Значения секретов не входят в клиентский bundle и репозиторий.

| Служба | Адрес | Назначение |
| --- | --- | --- |
| Convex | artificiallabs-convex.bebra42.ru | Клиентский backend |
| HTTP actions | artificiallabs-convex-site.bebra42.ru | Аутентифицированные HTTP операции |
| Dashboard | artificiallabs-convex-dashboard.bebra42.ru | Операторское управление |
| Expo Updates | artificiallabs-updates.bebra42.ru | Манифесты и проверка доступности |

Приватный sms-gateway доступен только в Docker-сети Convex и не имеет host port или FRP endpoint. Общий секрет шлюза и HMAC-секрет ограничителей остаются в серверном окружении. При определении клиентского IP требуется подтвердить, что отдельные соединения не схлопываются в один адрес прокси; иначе ограничения по IP будут иметь ошибочную область действия.

Одноразовые сообщения используют ASCII-формат в пределах одного SMS. До отправки нативный клиент сохраняет краткоживущую HMAC-подсказку платформы. Для iOS последняя строка связывает домен и код, для Android — хеш SMS Retriever. При изменении package name или сертификата подписи Android хеш вычисляется заново. Автозаполнение Android запускается до запроса отправки и не требует разрешения чтения SMS.

Шлюз не удаляет только что созданное исходящее сообщение сразу после успешной команды модема: подтверждение команды может предшествовать приёму оператором. Удаляется точное созданное шлюзом сообщение после истечения кода и дополнительного интервала. Проверки живой доставки выполняются вручную и не входят в периодический мониторинг.

Входящие SMS архивируются один раз в приватном файле с правами 0600 и HMAC-дедупликацией. Перед служебными операциями сохраняются только 16 новейших из 20 слотов модема, причём удаление старых разрешено после успешного архивирования. Сырой архив не передаётся в Convex, журналы, Git или консоль.

Запрос остатка SMS через *255*0# является глобальной ручной операцией с 24-часовым скользящим cooldown одновременно в Convex и шлюзе. Сохраняются только разобранное количество и безопасные статусы. Диагностика, CI и обычные E2E не должны инициировать USSD или реальную SMS-доставку.

## Контейнерные границы и постоянное состояние служб

Compose разделяет backend, dashboard и sms-gateway. Backend сохраняет состояние в томе /convex/data и предоставляет разные порты для клиентского API и HTTP actions; dashboard запускается после успешной проверки backend. Внутренний адрес SMS_GATEWAY_URL использует Docker DNS sms-gateway:8080. Шлюз имеет собственный постоянный том /data, необходимый для служебного состояния и архива входящих сообщений. Пересоздание контейнера и удаление его тома поэтому имеют принципиально разные последствия.

Публикация адресов Convex требует согласованных CONVEX_CLOUD_ORIGIN и CONVEX_SITE_ORIGIN. Это разные поверхности одного развёртывания: обычный ConvexReactClient подключается к backend, маршруты Auth и POST /document-ocr/page регистрируются в HTTP router и доступны через site. Перенаправление всех вызовов на один домен без учёта этого разделения может сохранить доступность процесса и одновременно нарушить прикладной контракт.

OTA работает от пользователя node с файловой системой контейнера read_only, отдельным томом /data и tmpfs /tmp на 64 МиБ. Закрытые материалы подключаются каталогом /run/secrets только для чтения; установлены no-new-privileges и cap_drop=ALL. Одноразовый data-init подготавливает владельца и права тома до запуска службы. База updates.sqlite, её журнал и каталог assets образуют связанный набор состояния; восстановление только таблиц без соответствующих ресурсов не обеспечивает пригодный к выдаче релиз.

Email-восстановление обращается напрямую к https://api.resend.com/emails с Bearer-авторизацией и AbortSignal.timeout(12000). Запрос несёт idempotency-key вида password-recovery/requestId. Ответ поставщика используется для извлечения безопасных дневных и месячных квот; ошибка доставки отмечает challenge как неуспешный. Ключ идемпотентности защищает повтор одной отправки у поставщика, но не заменяет собственное резервирование суточного лимита и проверку шестизначного кода.

## Сборка развёртывание и обновления приложения

Веб-публикация собирает статический admin/out и помещает его в nginx-образ ghcr.io/che548/artificiallabs. Runtime содержит экспорт и конфигурацию nginx, без исходников, .env, Git-метаданных и административных ключей. Публичная доступность образа требует проверять именно состав конечного слоя, а не только отсутствие секретов в клиентском коде.

Workflow Build and Publish Web Image запускается при push в main либо вручную для выбранной ветки. Он устанавливает зависимости, выполняет npm run verify, развёртывает Convex, проверяет generated bindings и публикует образ. Ручная публикация также обновляет latest, поэтому выделенный Watchtower разворачивает выбранную ревизию. Серверный ключ не передаётся workflow pull request.

Нативный выпуск отделён от веб-контейнера. Изменение SQLCipher-конфигурации, entitlement или нативного модуля требует новой development либо release сборки. Expo Go не подтверждает работу собственного нативного состава. Фактические идентификаторы приложения и подписи должны совпадать с привязками сервисов, Associated Domains и настройками доставки.

OTA использует self-hosted Expo Updates Protocol v1. Релизы разделены точным сочетанием платформы, fingerprint runtimeVersion и канала preview либо production. Клиентский канал по умолчанию — production. Контейнер службы слушает 127.0.0.1:8094; публичным входом служит выделенный FRP-туннель.

Ручной OTA workflow допускает операции только из main. publish-preview экспортирует текущий main. После проверки обеих платформ promote-production переводит уже проверенные update ID без пересборки bundle. Rollback меняет указатель канала для точного runtime. Непосредственная публикация новых байтов в production нарушает принятую последовательность.

Публичный сертификат подписи обновлений хранится в certs/ota-certificate.pem. Закрытый RSA-ключ и секрет публикации существуют только в защищённой конфигурации службы и GitHub Actions. Защита от неработоспособного обновления остаётся включённой. Для Android перед передачей APK сравниваются assets/fingerprint и результат expo-updates runtimeversion:resolve.

Откат OTA не откатывает автоматически серверную схему, локальные данные и нативный бинарник. Поэтому план выпуска должен отдельно определять совместимость каждой стороны. Новая серверная форма сначала поддерживает существующие клиенты; только затем можно выпускать клиента, который использует расширенный контракт.

## Устройство хранилища релизов и протокола выдачи

OTA-служба хранит метаданные в updates.sqlite, а ресурсы — отдельными файлами с именем SHA-256. Таблицы releases, assets и release_assets разделяют релиз, уникальные байты и связи между ними. До записи каждый ресурс декодируется, его хеш пересчитывается и сравнивается с заявленным; требуется ровно один launch asset. Идентификатор релиза выводится из хеша platform, runtimeVersion и упорядоченного списка хешей ресурсов. Порядок этого списка участвует в идентичности и должен сохраняться при воспроизводимой публикации.

Активация представлена добавлением записи в channel_history для точных channel, platform и runtime_version. Promote ссылается на существующий release ID, не создавая новые байты. Rollback выбирает предпоследнюю запись истории целевой комбинации и добавляет её как очередную активацию; при отсутствии второй записи возвращается NO_ROLLBACK_TARGET. Очистка сохраняет до десяти записей истории на комбинацию и удаляет релизы и ресурсы, на которые не осталось ссылок. Доступность отката поэтому ограничена сохранённой историей.

GET /api/manifest требует expo-protocol-version=1 и читает expo-platform, expo-runtime-version и expo-channel-name. Если подходящего релиза нет либо expo-current-update-id уже совпадает, возвращается HTTP 204. Иначе сервер выдаёт application/expo+json и expo-signature с keyid=main и alg=rsa-v1_5-sha256. Подпись вычисляется над точными байтами сохранённого JSON; изменение даже пробела после подписи меняет проверяемое сообщение. Ресурсы выдаются как immutable с ETag, равным хешу.

Внутренние POST-запросы аутентифицируются HMAC-SHA-256 над строкой timestamp.requestId.sha256(body). Допустимое расхождение времени — пять минут; сравнение подписи выполняется timingSafeEqual после проверки длины. requestId записывается в request_replays с уникальным ключом, поэтому повтор возвращает OTA_REPLAY. Этот протокол защищает управляющую публикацию и отличается от RSA-подписи, которой клиент проверяет сам манифест. Публичный сертификат не позволяет сформировать ни управляющий HMAC, ни подпись нового релиза.

## Последовательность выпуска и частично обновлённое окружение

Веб-образ собирается в два этапа: Node 22.13.1 Alpine устанавливает корневые и административные зависимости по отдельным lock-файлам и формирует admin/out; nginx 1.28 Alpine получает только статический экспорт и конфигурацию раздачи. NEXT_PUBLIC_CONVEX_URL передаётся как build argument и встраивается в клиентский JavaScript. Изменение переменной у уже запущенного nginx не перенастроит этот адрес: для смены backend нужен новый экспорт. .dockerignore исключает .env, Git, node_modules, output и локальные артефакты ещё из контекста сборки.

Workflow использует общую группу web-deploy с cancel-in-progress=false, поэтому параллельные запросы выпуска сериализуются без прерывания уже работающего задания. После проверки проекта выполняется развёртывание Convex и git diff --exit-code для generated bindings; только затем собирается и публикуется linux/amd64-образ. Если сборка контейнера завершается ошибкой после успешного обновления Convex, backend уже изменён, а прежний веб-клиент продолжает работать. Серверная совместимость обязательна именно для такого промежуточного состояния; workflow не создаёт общей транзакции между Convex и GHCR.

Watchtower опрашивает образ каждые 300 секунд и ограничен контейнером artificiallabs_web с разрешающей меткой. Его доступ к Docker socket относится к эксплуатационным полномочиям на узле. Тег latest удобен для обнаружения обновления, однако точную установленную версию следует определять по digest образа и метаданным commit. Возврат веб-образа не отменяет выполненное ранее развёртывание серверных функций.

OTA workflow выполняется на macos-15, поскольку iOS fingerprint должен вычисляться в Darwin-окружении. Скрипт дополнительно требует чистую рабочую копию main, экспортирует каждую платформу во временный каталог и включает commit в публичную конфигурацию. Публикация, продвижение и откат выполняют отдельные запросы для iOS и Android последовательно. Ошибка второй платформы может оставить первую уже обновлённой; перед повтором необходимо проверить оба фактических update ID и состояния каналов, сохранив успешно выполненную часть как отдельный результат выпуска.

## Подготовка входных файлов для воспроизводимого Android runtime

Совпадение lock-файла ещё не гарантирует совпадение входов fingerprint до и после нативной сборки. Зависимость masked-view версии 0.3.2 при использовании AGP 7 и выше удаляет атрибут package из собственного AndroidManifest.xml. Этот шаг изменяет файл в node_modules до вычисления fingerprint нативной сборки; чистый экспорт OTA без такой подготовки получил бы другой набор входных байтов.

prepareAndroidOtaInputs воспроизводит ровно это преобразование. Скрипт сначала проверяет точную версию пакета, затем SHA-256 исходного manifest. Уже подготовленный файл распознаётся по отдельному ожидаемому хешу, поэтому повторный запуск ничего не меняет. Для неизвестной версии, неожиданного содержимого или несовпадения результата предусмотрены разные ошибки, требующие пересмотра подготовки. Механизм не является универсальным патчем зависимостей: после их обновления необходимо заново подтвердить преобразование и сопоставить fingerprint установленного бинарного файла с runtime экспортируемого обновления.

## Наблюдаемость надёжность и проверка качества

Наблюдаемость разделена на локальную диагностику пользователя, административные проверки служб и согласованную техническую аналитику. Локальная диагностика показывает агрегированное состояние устройства и обновления. Она не является удалённым административным терминалом и не предоставляет серверные журналы, shell, медицинские значения или содержимое очереди.

Подвал профиля отображает версию приложения и сборки, commit и идентификатор обновления. Три нажатия за две секунды открывают диагностику в каждом нативном типе сборки, включая production. Выбор Production или Preview доступен в этом интерфейсе. Разрешены только грубые публичные /version и /health probes. PRAGMA quick_check запускается вручную; автоматический ремонт, VACUUM, checkpoint и удаление не являются функцией диагностического экрана.

Монитор Convex периодически проверяет службы и сохраняет безопасные статусы. nginx healthcheck подтверждает доступность процесса раздачи. Ответ healthy не доказывает успешный вход, проверку владельца или полное применение синхронизации. Внутренний монитор также зависит от той платформы, состояние которой он наблюдает.

Подробная аналитика требует самостоятельного согласия. Клиентская очередь ограничивает порцию 50 событиями, а сервер устраняет дубли по eventId. Административные отчёты читают материализованные дневные агрегаты. Сырые персональные таблицы и текст ошибок не должны использоваться как удобный источник аналитики.

Контроль качества включает проверки контрактов и политик, UI-тесты с искусственными данными, нативные сценарии и отдельно разрешённые live-проверки. Общий npm run verify объединяет предметные проверки, TypeScript, проверку Expo, Expo Doctor, веб-экспорт и верификацию admin. Этот агрегат не равен полному npm test и не заменяет все нативные и живые сценарии.

E2E backend работает с одноразовыми аккаунтами и точной административной очисткой. Веб-проверка относится к read-only demo, а консоль имеет отдельный UI-набор. Нативные сценарии используют Maestro. Секреты и артефакты живых проверок хранятся только в игнорируемых областях; workflow e2e-live остаётся ручным.

Для эксплуатационной оценки нужны показатели сохранности локальной записи, возраста очереди, успешности синхронизации, задержки авторизации и свежести публикаций. Числовые SLO, RPO и RTO требуют утверждённого окна измерения, владельца и доказанного восстановления. Само наличие тестов, тайм-аута или healthcheck не устанавливает такие обязательства.

При инциденте приоритетны сохранение локально завершённой записи, прекращение недопустимой внешней обработки, ограничение затронутой функции и возврат к совместимому артефакту. Очистка пользовательских данных не должна служить универсальным восстановительным действием.

## Идемпотентный приём и материализация технических агрегатов

Приём технических событий проверяет допустимый размер порции, отдельное аналитическое согласие и ограничение частоты. eventId должен соответствовать ограниченному формату; событие с тем же ключом находится по by_event_id и не вставляется повторно. Время события проверяется относительно окна хранения и допуска в будущее, durationMs — на конечность и диапазон от нуля до 60000. Клиентские значения размерностей дополнительно проходят ограничение формата и длины.

Рабочая мутация выбирает ограниченную порцию событий без processedAt и группирует приращения по дню, области и размерности. Отдельно накапливаются количество событий, исходы, количество измерений длительности и сумма длительностей. Последние два поля нельзя заменять средним без веса: для объединения порций требуется суммировать числитель и знаменатель. Административные графики читают материализованный результат, что отделяет стоимость открытия страницы от объёма исходных событий.

Для учёта дневной активности применяется HMAC от day:userId с серверным ANALYTICS_HASH_SECRET. Ключ меняется вместе с днём и проверяется по составному индексу, чтобы повторная активность не увеличивала дневное число пользователей. Это конкретная схема псевдонимизации счётчика, а не утверждение об анонимности любой статистики. Доступ к секрету и совмещение других данных остаются самостоятельными границами модели доступа.

## Смысл проверок доступности и ограничения мониторинга

Контейнерная проверка nginx обращается к статическому /health каждые 30 секунд с тайм-аутом 5 секунд и тремя допустимыми отказами. Она подтверждает способность nginx ответить, но не выполняет вход и не проверяет доступность Convex. Backend проверяется через /version с собственными интервалами; у OTA и SMS-шлюза отдельные /health. Настройки healthcheck не следует трактовать как автоматическое восстановление всех зависимостей: они описывают способ получения состояния контейнера.

checkServices выбирает только цели, для которых заданы серверные URL, и выполняет запросы с тайм-аутом 5 секунд. Успешный HTTP-ответ даёт healthy, иной HTTP-статус — degraded, транспортный сбой — offline с безопасным кодом TIMEOUT либо NETWORK_ERROR. Поэтому отсутствие настроенной цели отличается от зафиксированного отказа. Для site проверяется корневой адрес, и ответ 404 может характеризовать отсутствие маршрута, а не недоступность всего сервиса; разбор инцидента должен сопоставлять статус с проверяемым endpoint.

## Семантика нативных показателей ресурсов

DeviceDiagnostics возвращает числовой снимок процесса и устройства: число процессоров, накопленное процессорное время в миллисекундах, показатели памяти и ёмкость диска в байтах. processCpuTimeMs представляет сумму использованного времени, а не мгновенный процент загрузки. При расчёте нагрузки по двум снимкам необходимо делить приращение процессорного времени на прошедшее время наблюдения и явно выбирать нормирование по числу процессоров; одиночный снимок для такого процента недостаточен.

Одинаковые имена полей не обеспечивают полного равенства платформенных измерений. iOS получает resident_size через task_info, тогда как Android записывает в processRssBytes результат Debug.getPss, переведённый из КиБ в байты. PSS пропорционально распределяет общие страницы и не тождественен RSS. Аналогично availableMemoryBytes на iOS основан на os_proc_available_memory, а на Android — на ActivityManager.MemoryInfo.availMem. Эти величины пригодны для наблюдения динамики в одном окружении, но требуют оговорки при прямом межплатформенном сравнении.

При невозможности получить отдельные iOS-показатели реализация может вернуть ноль. Нулевое значение в таком снимке нельзя автоматически считать доказательством отсутствия занятой памяти или свободного диска. Диагностический отчёт должен сохранять смысл источника измерения и сопоставляться с состоянием приложения, не превращая агрегатные значения в подробную инвентаризацию файлов или содержимого базы.

## Восстановление состояния по границам хранения

Нативное хранилище, Convex, статический веб-образ, OTA и состояние SMS-шлюза восстанавливаются разными способами. Первая задача при инциденте — сохранить завершённые локальные записи и установить, какая операция действительно подтверждена. Очистка приложения не является штатным способом устранения сетевого сбоя.

Для Convex нужен согласованный набор базы и файлового состояния, версия образа и защищённая конфигурация экземпляра. Копия активного каталога без учёта WAL и записи не доказывает возможность восстановления. Для OTA сохраняются `updates.sqlite`, связанный журнал и каталог assets; проверяется соответствие ссылок фактическим байтам. Закрытый ключ подписи и секрет управляющих запросов восстанавливаются через отдельный защищённый процесс. Архив SMS-шлюза остаётся внутри приватного эксплуатационного контура.

Учебное восстановление выполняется в изолированном окружении с отключённой внешней доставкой и автоматическими обращениями к поставщикам. Последовательно проверяются запуск служб, схема и индексы, вход синтетического пользователя, изоляция владельцев, запись и синхронизация, чтение статического admin, подпись OTA и доступность всех assets. Положительный `/health` недостаточен.

RPO описывает допустимый интервал потери данных, RTO — время восстановления. Эти величины устанавливаются только после проверки реального процесса и расписания копий; репозиторий сам по себе не подтверждает выполнение числового обязательства. На устройстве SecureStore-ключ не переносится вместе с JSON-экспортом. Облачная реплика не содержит оригиналов документов, поэтому не является полной резервной копией телефона.
