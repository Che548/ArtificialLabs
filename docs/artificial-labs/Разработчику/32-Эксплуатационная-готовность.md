# Эксплуатационная готовность

Эксплуатационная готовность означает, что версию можно не только развернуть, но и безопасно наблюдать, поддерживать, ограничивать при отказе и восстанавливать.

> [!warning] Текущий статус
> Код содержит локально устойчивую запись, проверки состояния и защищённый выпуск веб-образа. Репозиторий не подтверждает резервное копирование Convex, числовые RPO и RTO, внешний сквозной монитор, доставку оповещений, график дежурств и рабочий канал поддержки. Поэтому полная готовность к эксплуатации требует внешних решений.

## Критерии готовности

Версия готова к сопровождению, когда:

1. точный коммит и артефакты однозначно идентифицированы;
2. для каждого компонента назначены владелец и заместитель;
3. известны обязательные проверки и результаты для затронутых платформ;
4. отказ обнаруживается свежим и безопасным сигналом;
5. оповещение доходит до ответственной роли;
6. безопасное ограничение функции не уничтожает данные и не расширяет доступ;
7. предыдущая исправная версия известна по SHA или дайджесту;
8. восстановление данных и полномочий испытано;
9. поддержка знает, какие сведения можно собирать;
10. открытые риски имеют владельца и срок.

Успешный `npm run verify` закрывает только часть этих требований.

## Компоненты и безопасный отказ

| Компонент | Признак работоспособности | Безопасное поведение при отказе | Ответственная роль |
|---|---|---|---|
| Нативный клиент | запуск, открытие SQLCipher, локальное сохранение | ввод продолжается без сети; завершённая запись остаётся на устройстве | мобильная разработка |
| Локальная база и очередь | транзакция чтения и записи, подтверждение точных элементов | неподтверждённый элемент остаётся в очереди | данные |
| Синхронизация | профиль и пакет переданы, подтверждённая очередь пуста | временный отказ повторяется ограниченно; ошибки входа и валидации не повторяются как транспортные | данные и сервер |
| Convex | `/version`, Auth и предметная функция отвечают | клиент остаётся локальным; опасные серверные операции прекращаются | серверная разработка |
| StripCV | нативная сборка, CTest, результат по схеме | сомнительный результат требует повторной съёмки и подтверждения | компьютерное зрение и качество |
| Уведомления | системное разрешение и тестовое локальное уведомление | без APNs или FCM работают локальные напоминания | мобильная разработка |
| Административная консоль | `/health`, вход, `requireAdmin()`, критические запросы | медицинские данные не открываются; используется предыдущий образ | платформа и безопасность |
| Каталог и калибровки | валидированный ресурс, подпись, публикация и аудит | без ключа или проверки публикация запрещена | сервер и безопасность |
| Телеметрия | приём, обработка, очистка и ограниченный обзор | медицинская запись не зависит от доставки события | данные и безопасность |
| ИИ | выключенное состояние, отдельное согласие и серверные флаги | недоступность поставщика оставляет локальные данные и безопасный резервный план | продукт и безопасность |
| GitHub Actions | ожидаемые проверки, разрешения и метки образа | недоверенный код не получает производственные секреты | платформа |

## Обязательные проверки

Базовый набор:

```bash
npm test
npm run e2e:coverage
npm run verify
```

В зависимости от изменения добавляются:

```bash
npm run test:strip-cv
npm run e2e:backend
npm run e2e:web
npm run e2e:native
```

Для `admin/` отдельно выполняют чистую установку и проверку:

```bash
npm --prefix admin ci
npm --prefix admin run verify
```

Живые и нативные проверки запускают только в разрешённой среде. Невыполненная проверка из-за отсутствия устройства или реквизитов не считается успешной.

Подробное соответствие областей и наборов находится в [[Разработчику/28-Матрица-приёмочных-проверок|матрице приёмки]].

## Наблюдение

Для каждой критической пользовательской операции должны быть известны:

- условие успеха;
- допустимая задержка;
- источник и свежесть сигнала;
- безопасные поля;
- порог отклонения;
- получатель оповещения;
- первое действие.

Текущие `/health`, `/version` и `serviceChecks` подтверждают только доступность отдельных процессов. Они не проверяют полный вход, запись, синхронизацию и административное чтение. При полном отказе Convex внутренний монитор не сможет записать собственную ошибку.

Пока внешний монитор, доставка оповещения и SLO не утверждены, состояние описывают как открытый эксплуатационный пробел.

## Поддержка и инциденты

До рабочего выпуска организация должна назначить:

- канал регистрации обращений;
- владельца первой реакции;
- инженерного и безопасностного получателя эскалации;
- владельца решения об ограничении или возврате;
- заместителей и график доступности;
- правила хранения карточек и вложений.

В обычный канал не принимают пароли, токены, медицинские файлы, полный экспорт и необработанные журналы. Подробный процесс описан в [[Разработчику/40-Поддержка-и-эскалация|руководстве поддержки]].

## Восстановление

До допуска должны быть определены:

- предыдущий исправный коммит;
- дайджест предыдущего веб-образа;
- совместимость серверной схемы при возврате;
- последняя пригодная резервная копия Convex;
- оператор восстановления;
- проверка данных, входа и полномочий после операции.

Рабочие данные нельзя удалять ради упрощения возврата версии. Возврат кода Convex без плана для уже изменённых данных запрещён.

Постоянный Docker-том сам по себе не заменяет резервную копию. До утверждения и выполнения учебного восстановления RPO и RTO остаются неизвестными.

## Внешние решения

Репозиторий не может определить:

- владельцев и заместителей по именам;
- числовые SLO, SLA, RPO и RTO;
- график дежурств;
- канал поддержки и аварийный контакт;
- место, частоту и срок хранения резервных копий;
- срок внешних журналов и материалов расследования;
- обязательное утверждение выпуска во внешней системе.

Эти элементы должны быть оформлены вне Git и связаны с паспортом выпуска. Их отсутствие нельзя скрывать формулировкой «готово к эксплуатации».

## Запись проверки готовности

Итог содержит:

- полный SHA и состав изменения;
- платформы и артефакты;
- выполненные команды и результаты;
- состояние наблюдения и доставки оповещений;
- владельцев сопровождения и восстановления;
- предыдущую исправную версию;
- открытые исключения и сроки;
- решение владельца эксплуатации.

Секреты, медицинские значения, исходные файлы и полные журналы в итог не включают.

## Условия запрета

Эксплуатационный допуск запрещён, если:

- нарушена локальная запись или принадлежность данных;
- нет способа безопасно выключить рискованную функцию;
- критический отказ нельзя обнаружить или передать владельцу;
- неизвестна предыдущая исправная версия;
- изменение схемы не имеет совместимого возврата;
- секрет присутствует в образе или артефакте;
- восстановление зависит от непроверенной копии;
- открытый риск не имеет владельца и срока.
