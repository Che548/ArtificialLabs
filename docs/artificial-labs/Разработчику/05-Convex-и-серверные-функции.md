# Серверные функции Convex

## Серверные контракты и контроль доступа

Convex объединяет схему данных, реактивные запросы, транзакционные изменения и действия для внешних операций. query читает данные, mutation изменяет их в серверной транзакции, action организует работу с внешней зависимостью. Файлы convex/_generated предоставляют типизированные ссылки; фактическую семантику задают валидаторы и обработчики в convex/.

requireUserId проверяет аутентифицированную серверную идентичность. requireActiveAccount дополнительно запрещает работу с учётной записью, ожидающей удаления. requireOwnedProfile получает профиль текущего владельца. requireAdmin подтверждает действующее административное членство. Передача идентификатора объекта из интерфейса не заменяет ни одну из этих проверок.

| Поверхность | Условие доступа | Примеры ответственности |
| --- | --- | --- |
| Персональные функции | Вход активность и владение | Профиль записи история |
| ИИ-действия | Доступ согласие флаг и квота | Диалог и проверка плана |
| Административные функции | requireAdmin | Роли контент и агрегаты |
| Публичные запросы | Неперсональная проекция | Опубликованный контент |
| Внутренние функции | Доверенный серверный вызов | Очистка и фоновые задания |

Публичный ответ должен формироваться как отдельная проекция. В нём не должны появляться черновики, сведения об авторах административных изменений, внутренние заметки или персональные поля. Клиентская фильтрация уже полученного широкого объекта не защищает такие данные.

Действия, продолжаемые после обращения к поставщику, повторно проверяют разрешения и состояние. Между началом запроса и ответом пользователь может отключить функцию или отозвать согласие. Поэтому первоначальная проверка не является бессрочным разрешением применить результат.

Идемпотентность определяется предметным ключом и способом резервирования. localId защищает синхронизацию, eventId — приём телеметрии, а requestId некоторых ИИ-операций — повторную отправку поставщику. В административном аудите requestId служит корреляции и сам по себе не превращает любое изменение в идемпотентное.

Эволюция API требует совместимости одновременно работающих клиентов. Сначала вводится серверная форма, поддерживающая старое и новое представление, затем выпускается клиент; удаление переходной формы допустимо после подтверждения её ненужности. Изменение кода ошибки, лимита или трактовки поля может нарушить контракт даже при успешной компиляции TypeScript.

## Проверки на границах длительной операции

Получение профиля производится по индексу by_user с идентификатором, извлечённым из Convex Auth. requireOwnedProfile сначала проверяет активность аккаунта, затем требует существующий профиль; отсутствие профиля возвращает PROFILE_REQUIRED. Поэтому вход, завершение первичного заполнения и доступ к конкретной операции не следует объединять в один клиентский флаг. Серверный обработчик выбирает необходимую комбинацию проверок независимо от состояния экрана.

Для внешней операции полезно различать резервирование попытки, обращение к поставщику и допуск результата. В OCR эти этапы представлены reserve, непосредственным вызовом поставщика в HTTP action и finish с повторной проверкой access. Изображение не является аргументом внутренних мутаций: reserve получает userId, идентификаторы задания и попытки, номера страниц и версию согласия; finish — идентификаторы и признак успеха. Таким образом, служебный учёт ограничивается состоянием запроса, а не его содержимым.

## Карта серверных контрактов

| Модуль | Вход и назначение | Граница результата |
| --- | --- | --- |
| `health` | Владелец, localId, версии, структурированный batch | Реплика и ограниченный снимок; локальные пути исключаются клиентской проекцией |
| `agent` / `agentAction` | Вопрос, ограниченный контекст, request и continuation | Ответ, ссылки на источники, служебная генерация; ограниченные шаги |
| `agentPlan` | Разрешённый контекст и событие пересмотра | План и правила после проверки предметной политики |
| `documentOcrHttp` | Auth, JPEG страницы, версия, идентификаторы попытки | Транзитный ответ; без записи содержимого в Convex |
| `documentOcr` | Статус согласия, резервирование и завершение | Безопасные метаданные квоты и состояния |
| `documentInterpretation` | Выбранный текст и отдельный допуск | Ограниченное объяснение, без автоматического подтверждения строк |
| `registrationConsent` | Квитанция нового аккаунта и версия политики | Атомарная активация допустимых согласий |
| `adminUsers` | Администратор, курсор, фильтр | Только ID, email, дата регистрации, статус |
| `todayContent` | Публичное чтение либо административная правка | Опубликованная проекция либо версия черновика |
| `telemetry` | Допустимые события или суточная активность | Идемпотентный приём и дневные агрегаты |

Типизированная ссылка из `_generated/api.d.ts` не заменяет проверку входа на сервере. Внешний потребитель может обойти клиентский тип. Контракт включает пределы коллекций и строк, код отказа, проверку владельца, семантику повтора и побочный эффект. Несовместимость может возникнуть без изменения имени функции: например, при изменении сортировки снимка, трактовки отсутствующей даты либо срока продолжения.

## Фактическая серверная граница согласия

Политика штатного клиента требует явного согласия устройства до чтения медицинского снимка и отправки исходящей очереди. Однако текущий серверный контракт не реализует эту проверку одинаково для всех сущностей. `health.snapshot` вызывает `requireOwnedProfile`, но не проверяет `consentToCloudSyncAt`. `health.syncBatch` проверяет этот маркер только при наличии элементов плана, правил агента либо событий рекомендаций.

Следовательно, Auth, активность аккаунта и владение подтверждены серверным обработчиком, а универсальный запрет обмена без согласия пока опирается на клиентскую политику. Прямой авторизованный вызов обычных коллекций нельзя описывать как защищённый общей серверной проверкой согласия. Это ограничение реализации, а не разрешение расширять обработку. Усиление границы потребует отдельного изменения API с оценкой старых клиентов, регистрационной активации и порядка создания профиля.

Документные действия, регистрационная квитанция и допуск агента имеют собственные проверки. Их наличие не распространяется автоматически на `health.snapshot`. Матрица разрешений должна указывать конкретный обработчик и момент проверки, включая повторную проверку после внешнего ожидания. Обновление описания не меняет эти обработчики и не активирует серверные флаги.
