# Документация для разработчиков и сопровождения

## Назначение платформы и архитектурная концепция

«сфера.» — мобильное приложение проекта ArtificialLabs для ведения персональных данных о здоровье, работы с лабораторными результатами и документами, планирования наблюдения и диалога с интеллектуальным помощником. Продуктовая модель охватывает наблюдение за циклом, планирование беременности и беременность. Профиль задаёт контекст интерфейса, но не превращает пользовательские записи или ответы модели в медицинское заключение.

Основное архитектурное решение — приоритет локального хранения. Нативный клиент фиксирует структурированные данные в зашифрованной базе на устройстве. Серверная синхронизация подключается по явному выбору пользователя на конкретном устройстве. Такая организация сохраняет возможность вести записи при временной недоступности серверов и позволяет разграничить хранение, передачу данных и применение ИИ.

Платформа разделена на мобильное приложение, персональную серверную часть, административную консоль и эксплуатационные службы. Приложение предоставляет пользовательские сценарии; Convex выполняет авторизацию и обработку разрешённых структурированных данных; консоль управляет неперсональными справочниками, публикациями и доступом администраторов. Службы доставки сообщений и обновлений имеют собственные ограничения и секреты.

Для проектирования существенны четыре независимых признака: пользователь аутентифицирован, учётная запись активна, операция разрешена её владельцу, на соответствующую обработку получено действующее согласие. Проверка одного признака не заменяет остальные. Доступность внешнего поставщика и серверный флаг дополнительно ограничивают исполнение отдельных функций.

White paper предназначен для архитекторов, разработчиков мобильной и серверной частей, специалистов по эксплуатации и технических руководителей. Он раскрывает устройство платформы, семантику данных, границы доверия, эксплуатационные процедуры и критерии проверки. Зафиксированная техническая модель позволяет оценивать изменения как изменения контракта между устройством, сервером и внешними службами, а не только как правки отдельных экранов.

Технические гарантии относятся к конкретной области: транзакция защищает локальную запись, проверка владельца ограничивает серверный доступ, а подтверждение пользователем фиксирует проверку перенесённых данных. Ни одна из этих мер сама по себе не подтверждает клиническую достоверность, сертификацию продукта или выполнение количественного SLA.

## Компоненты системы и технологическая основа

Мобильная часть построена на Expo SDK 54 и React Native. В package.json заявлены Expo ~54.0.37, React Native 0.81.5, React 19.1.0, Expo Router ~6.0.24 и TypeScript ~5.9.2. Диапазоны зависимостей выражают допустимые версии; воспроизводимый состав установки определяется package-lock.json.

Навигационные маршруты находятся в app/, повторно используемые представления — в components/, предметная логика и платформенные адаптеры — в lib/. Каталог shared/ содержит контракты, которые должны одинаково трактоваться клиентом и сервером. design-system/ объединяет токены и визуальные примитивы; plugins/ вносит изменения в генерируемые нативные проекты.

Платформенные реализации отделяются суффиксами .native и .web. Это позволяет сохранять единый предметный интерфейс, не выдавая браузерную реализацию за эквивалент SecureStore, SQLCipher или системной фоновой задачи. Нативные модули документов, диагностики и автозаполнения SMS образуют явные границы между TypeScript и API операционной системы.

| Компонент | Технологии | Ответственность |
| --- | --- | --- |
| Мобильный клиент | Expo 54 и React Native | Интерфейс и локальные операции |
| Локальные данные | expo-sqlite и SQLCipher | Транзакции и исходящая очередь |
| Сервер | Convex и Convex Auth | Доступ и серверные контракты |
| Административная часть | Next.js 16.3.2 и React | Защищённое управление |
| Стили приложения | NativeWind 4 и токены | Общие правила оформления |
| Доставка веб-приложения | nginx и Docker | Раздача статического экспорта |

Консоль находится в отдельном пакете admin/. Она собирается в статический экспорт Next.js и развёртывается независимо от Expo web. Наличие общего репозитория не означает общего доверенного окружения: публичные переменные мобильного и веб-клиента принципиально отделены от серверных секретов.

Кодом мобильного жизненного цикла управляет корневой layout. Провайдеры авторизации, локального состояния, связи, уведомлений и обновлений дополняются менеджерами фоновой предметной работы. Экран подписывается на состояние подсистемы, а не должен единолично владеть длительной операцией, которая обязана переживать переход между вкладками.

## Разделение предметной логики и платформенных портов

Показательный пример организации зависимостей — runDocumentOcrJob. Исполнитель получает порты allowed, save, render, send и requestId. Его алгоритм не открывает нативный файл и не обращается к HTTP самостоятельно: эти действия предоставляются вызывающей стороной. Поэтому порядок сохранения маркеров и обработки ответа можно проверить независимо от PDFKit, PdfRenderer и сетевого транспорта. Платформенный адаптер отвечает за ресурс и формат, предметный исполнитель — за допустимый переход состояния.

Общие TypeScript-типы обеспечивают согласование сборки, а функции разбора проверяют недоверенные данные при исполнении. Для новой возможности недостаточно добавить поле в интерфейс: необходимо согласовать локальное чтение, экспорт, облачную проекцию, серверный валидатор и обратное слияние. Практически это разные границы совместимости. Например, допустимое локальное поле документа может намеренно отсутствовать в серверной форме; автоматическое распространение всех свойств объекта разрушило бы такое разделение.

## Подготовка локальной среды и воспроизводимая установка

Исходный состав задаётся `package.json`, корневым `package-lock.json`, отдельным lock-файлом `admin/` и нативной конфигурацией. В корне требуется Node не ниже 20.19.4; для воспроизведения CI следует использовать версию из `.nvmrc`. Не следует смешивать изменение зависимостей с запуском уже зафиксированного состава.

```sh
npm ci
npm --prefix admin ci
cp .env.example .env.local
npm run start
```

После заполнения публичного URL Expo подключается к выбранному backend. Привилегированный ключ требуется CLI, но не приложению. Команда `npm run convex:codegen` генерирует привязки; `npm run convex:deploy` выполняет реальное развёртывание функций в указанное окружение. Это разные по последствиям действия.

```sh
npm run check:expo
npm run typecheck
npm run typecheck:convex
npm --prefix admin run verify
```

Нативное приложение запускается через `npm run ios` или `npm run android`. SQLCipher, собственные модули, плагины защиты данных и SceneDelegate требуют development/release-сборки. Expo Go не подтверждает наличие этих возможностей. Генерируемые платформенные каталоги изменяются через конфигурацию и плагины; после prebuild проверяется, что требуемые изменения воспроизводятся.

`npm run build:expo-web` создаёт демонстрационный экспорт Expo. `npm run build:web` собирает защищённую административную часть. Проверка одного экспорта не подтверждает другой. Для редактирования статей есть локальный `npm run preview:admin-ui`; этот стенд использует искусственные данные и не является рабочей административной средой.
