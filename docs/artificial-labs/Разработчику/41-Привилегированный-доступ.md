# Привилегированный доступ

В ArtificialLabs есть одна прикладная административная роль — `admin`. Она даёт доступ к административной консоли, управлению каталогом и калибровками, публикации материалов, обезличенной аналитике, наблюдению, членствам администраторов и журналу административных действий.

> [!important] Главная граница
> Право на каждую защищённую операцию проверяет серверная функция `requireAdmin()`. Скрытый элемент интерфейса, защищённый маршрут и значение `viewer.isAdmin` сами по себе ничего не разрешают.

В текущей реализации нет отдельных ролей оператора, аудитора, редактора или утверждающего. Также репозиторий не подтверждает многофакторную аутентификацию, автоматическую переаттестацию доступа, аварийную учётную запись и обязательное согласование двумя сотрудниками. Такие меры нельзя считать действующими только на основании внутренней договорённости команды.

## Поверхности привилегированного доступа

| Поверхность | Как предоставляется доступ | Что защищает доступ | Основное ограничение |
|---|---|---|---|
| Административная консоль | действующее членство в `adminMemberships` | `requireAdmin()` в каждой серверной операции | клиентская проверка используется только для интерфейса |
| Внутренние функции Convex | административный ключ и доверенная среда | функции `internalQuery` и `internalMutation` не публикуются в клиентском API | защита ключа и вызывающего задания остаётся обязательной |
| GitHub Actions | разрешения задания, секреты репозитория и краткоживущий `GITHUB_TOKEN` | набор секретов зависит от события и задания | код из запроса на слияние не должен получать производственные секреты |
| Среда Convex и инфраструктура | внешние переменные окружения | секреты не входят в клиентскую сборку и образ | репозиторий не управляет их ротацией и сроком действия |

Обычная аутентифицированная учётная запись не получает административных прав. Для пользовательских данных продолжают действовать проверки активности учётной записи, принадлежности профиля и отдельных согласий.

## Обязательные правила

1. Каждая новая административная функция самостоятельно вызывает `requireAdmin()`.
2. Клиент получает только данные, необходимые для текущего экрана или действия.
3. Изменяющая операция записывает административное событие без секретов, медицинских значений и свободного пользовательского текста.
4. Публичные переменные `EXPO_PUBLIC_*` и `NEXT_PUBLIC_*` не содержат секретов.
5. Задание, выполняющее код из запроса на слияние, не получает административный ключ Convex и производственные учётные данные.
6. Самоназначение администратора через публичный API запрещено.
7. Отзыв последнего действующего администратора запрещён до подготовки проверенного способа восстановить управление.
8. Организационные меры считаются действующими только при наличии утверждённой внешней процедуры и записи о её выполнении.

## Жизненный цикл роли `admin`

### Запрос и согласование

Репозиторий не содержит системы заявок и не определяет, кто должен согласовывать административный доступ. До назначения организация должна зафиксировать вне Git:

- деловую необходимость и требуемый объём доступа;
- лицо, согласовавшее выдачу;
- владельца доступа;
- дату следующего пересмотра;
- условие досрочного отзыва.

В документацию проекта не помещают персональные сведения сотрудников, номера внутренних заявок с закрытыми данными и служебные реквизиты.

### Первичное назначение

Первого администратора назначают внутренней функцией `admin:bootstrapByEmail`. Пользователь с указанным адресом уже должен существовать. Функция проверяет, что действующего администратора ещё нет, создаёт членство и записывает событие `admin.bootstrap`.

Команду запускают только в доверенной среде с реквизитами нужного развёртывания:

```bash
npx convex run admin:bootstrapByEmail '{"email":"admin@example.com"}' --env-file .env.local
```

Адрес в примере условный. Файл `.env.local`, административный ключ и вывод с чувствительными данными не сохраняют в Git и не прикладывают к общедоступным отчётам.

Событие `admin.bootstrap` указывает назначенного пользователя как инициатора. Оно не позволяет установить человека, который фактически запустил команду. Эту связь необходимо сохранять во внешней заявке или журнале доступа к инфраструктуре.

### Назначение дополнительных администраторов

Операция `admin.grant` доступна только действующему администратору и только для уже зарегистрированного пользователя. Она создаёт членство либо повторно активирует отозванное, сохраняет инициатора и записывает событие `admin.grant` с `requestId`.

Если пользователь уже является действующим администратором, операция возвращает существующий идентификатор и не создаёт новое событие. Поэтому успешный повторный вызов не подтверждает повторное согласование доступа.

`requestId` помогает связать действия внутри приложения, но не заменяет номер заявки и не доказывает согласование независимым лицом.

### Использование

Защищённые функции в `convex/admin.ts`, `convex/adminCatalog.ts`, `convex/monitoringData.ts` и административной части телеметрии вызывают `requireAdmin()`. Списки используют курсорную пагинацию и ограничивают число и объём прочитанных записей.

При добавлении функции проверяют:

- вызов `requireAdmin()` внутри самой функции;
- минимальный состав ответа;
- пределы чтения и пагинацию;
- отсутствие секретов и чувствительных данных в ошибках;
- административный аудит для изменения состояния;
- поведение при повторном запросе;
- отрицательный сценарий для обычного пользователя и отозванного администратора.

Административная консоль не должна получать личные медицинские записи. Расширение её полномочий на такие данные требует отдельного пересмотра модели угроз, целей обработки и испытаний авторизации.

### Периодический пересмотр

Консоль показывает действующие и отозванные членства, но в модели нет срока действия роли, автоматического пересмотра и блокировки при просрочке. Организация должна отдельно определять периодичность проверки.

Во время пересмотра для каждого действующего членства подтверждают владельца, актуальную деловую необходимость, последнее ожидаемое использование и дату следующего решения. Результат хранят вне репозитория. Сам просмотр списка в консоли не считается переаттестацией.

### Отзыв

Операция `admin.revoke` требует действующего администратора, сохраняет инициатора и время и записывает событие `admin.revoke`. Сервер отклоняет отзыв последнего активного членства ошибкой `LAST_ADMIN_REQUIRED`.

При срочном закрытии доступа сначала отзывают роль, затем завершают доступные сеансы и оценивают необходимость замены секретов. Текущий код не подтверждает автоматическое завершение всех активных сеансов после отзыва роли.

### Удаление учётной записи

Активный администратор не может запросить удаление своей учётной записи: сервер возвращает `REVOKE_ADMIN_BEFORE_ACCOUNT_DELETION`. После отзыва действует обычный жизненный цикл пользователя.

`permanentlyDeleteUser()` не содержит явного удаления `adminMemberships`, `adminAuditEvents` и авторства опубликованных материалов. Срок хранения этих записей должна определять отдельная утверждённая политика. По текущему коду нельзя обещать ни их полное удаление, ни бессрочное сохранение.

## Секреты и места хранения

| Секрет | Назначение | Допустимое место | Запрещённое место |
|---|---|---|---|
| `CONVEX_SELF_HOSTED_ADMIN_KEY` | развёртывание функций, служебный CLI и защищённые E2E | `.env.local`, секрет GitHub Actions | запрос на слияние, журнал, Docker-образ, артефакт испытаний |
| `JWT_PRIVATE_KEY`, `JWKS` | Convex Auth | среда Convex | клиентская переменная и Git |
| `CALIBRATION_SIGNING_PRIVATE_KEY` | подпись калибровок | среда Convex | `NEXT_PUBLIC_*`, аргумент сборки и образ |
| `ANALYTICS_HASH_SECRET` | формирование необратимого аналитического ключа | среда Convex | ответ административного API и клиентская сборка |
| `INSTANCE_SECRET` | управление самоуправляемым Convex | локальная инфраструктурная среда | Git и общедоступный журнал |
| реквизиты APNs, FCM и поставщика ИИ | удалённые уведомления и ИИ | защищённая среда соответствующего сервиса | мобильное приложение, веб-сборка и Git |
| учётные данные E2E-администратора | защищённые сквозные испытания | секреты вручную запускаемого задания | запрос на слияние и публикуемый артефакт |

Код не задаёт периодическую ротацию, предельный возраст секрета и реестр владельцев. Эти требования должны выполняться средствами инфраструктуры и подтверждаться отдельно.

## Границы GitHub Actions

`ci.yml` запускается при отправке изменений и для запросов на слияние. Задание имеет только `contents: read`, не получает административный ключ Convex и не выполняет развёртывание.

`e2e-live.yml` запускается вручную. Оно получает административный ключ и учётные данные E2E, развёртывает выбранные функции и сохраняет ограниченный артефакт на 14 дней.

`ghcr-publish.yml` запускается для `main` или вручную. Задание получает `packages: write`, развёртывает Convex и публикует веб-образ. Административный ключ передаётся только шагу развёртывания, а не как аргумент сборки Docker.

В репозитории нет `CODEOWNERS` и конфигурации GitHub Environment с обязательным утверждением. Защита ветвей и другие правила могут быть настроены в GitHub, но код их не подтверждает.

## Разделение обязанностей

Роль `admin` объединяет несколько стадий управления каталогом и содержимым. Модель сохраняет `authorId` и `reviewerId`, но не запрещает их совпадение. Одно задание публикации развёртывает серверные функции и выпускает веб-образ.

Следовательно, независимое утверждение двумя участниками не реализовано как техническое ограничение. Если оно обязательно, потребуются отдельные роли или серверная проверка несовпадения исполнителей, миграция данных, изменения интерфейса, аудит отказов и автоматические испытания.

## Административный аудит

`adminAuditEvents` хранит инициатора, действие, тип и идентификатор объекта, краткое описание длиной до 500 символов, `requestId` и время. Журнал помогает восстановить последовательность операций, но код не подтверждает:

- неизменяемое внешнее хранилище;
- экспорт и резервное копирование;
- утверждённый срок хранения;
- глобальную уникальность `requestId`;
- автоматическое оповещение о рискованном действии;
- связь с внешней заявкой.

Описание события не должно содержать секреты, медицинские показатели, содержимое файлов и свободный текст пользователя. Снимок адреса администратора в членстве относится к чувствительным персональным данным.

## Действия при подозрении на компрометацию

1. Зарегистрировать инцидент и безопасно сохранить время, затронутую учётную запись и известные операции.
2. Отозвать роль, если существует другой действующий администратор.
3. Завершить доступные сеансы средствами системы аутентификации.
4. Заменить только затронутые секреты во всех местах их использования.
5. Проверить административный аудит, историю GitHub Actions, опубликованные образы и изменения каталога.
6. При необходимости вернуть проверенный неизменяемый артефакт.
7. Зафиксировать остаточный риск и ограничения атрибуции.

Последнего администратора не отзывают без заранее проверенного способа восстановить управление. Владельцев аварийного решения и порядок восстановления необходимо утвердить вне репозитория.

## Проверка изменения

Минимальный набор воспроизводимых проверок:

```bash
npm test
npm --prefix admin run verify
npm run e2e:web
```

`convex/admin.test.ts` проверяет одноразовое первичное назначение, запрет самоназначения, аудит выдачи и отзыва, защиту последнего администратора и административный доступ к каталогу. Эти испытания не подтверждают внешнее согласование, многофакторный вход, ротацию секретов и периодическую переаттестацию.

## Условия запрета выпуска

Изменение нельзя выпускать, если:

- серверная операция полагается только на проверку в интерфейсе;
- административный ответ содержит лишние персональные или медицинские данные;
- изменяющая операция не оставляет безопасную запись аудита;
- производственный секрет доступен заданию запроса на слияние;
- секрет передаётся клиенту, в аргументы сборки или публикуемый образ;
- отзыв может оставить систему без управляемого администратора;
- для новой привилегии не определены назначение, отзыв и проверка;
- неизвестно, как восстановить управление после компрометации.
