## Три раздела Vault

`Общее` задаёт границы продукта и единые правила. `Пользователю` содержит инструкции без внутренних адресов, секретов и служебных команд. `Разработчику` описывает реализацию, проверку, выпуск и эксплуатацию.

На каждой странице есть ссылки по теме и короткая строка навигации внизу. Устойчивый `document_id` не меняется при переименовании файла.

## Что означают свойства заметки

| Свойство | Как его читать |
|---|---|
| `status: active` | Описанное поведение входит в текущий контракт проекта. |
| `status: deferred` | Код или интерфейс может существовать, но функция ещё не обещана пользователю. |
| `audience` | Показывает, для кого написана заметка: пользователя, команды или обеих групп. |
| `updated` | Дата последнего изменения текста. |
| `reviewed_on` | Дата последней проверки фактов. |
| `verified_commit` | Коммит, с которым сверяли утверждения. |

Редакционная правка не делает факты автоматически актуальными. Поэтому `updated` может быть новее, чем `reviewed_on`.

## На какие источники можно опираться

Основанием служат отслеживаемый код, тесты, конфигурация, `AGENTS.md` и публичные обещания из `README.md`. Неотслеживаемые каталоги, временные результаты, медицинские образцы и локальные секреты не подтверждают наличие функции.

Если код и заметка расходятся, доверять нужно коду и обязательным правилам проекта. Неясность отмечается прямо; её нельзя скрывать словами «обычно», «как правило» или «должно работать».

## Как написаны страницы

1. В начале дан ответ, ограничение или цель действия.
2. Шаги используются только там, где важен порядок.
3. Таблицы оставлены для сравнения, а не для длинных пояснений.
4. Один абзац раскрывает одну мысль.
5. Русский термин предпочтительнее англоязычной кальки. Имена технологий, команды, пути и идентификаторы сохраняют исходное написание.
6. Ограничение стоит рядом с обещанием, которое оно уточняет.

Подробный порядок проверки и обновления описан в [[Общее/05-Управление-документацией|правилах сопровождения документации]].
