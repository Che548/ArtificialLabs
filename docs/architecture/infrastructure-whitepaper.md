## 1. Резюме

Сейчас прикладной backend «Сферы» работает на junk: одна инстанция self-hosted
Convex с SQLite/filesystem, рядом статическая админка/страница установки,
приватный SMS gateway и OTA-сервис. Публичные точки входа используют отдельные
VPS Fred. PostgreSQL и Kubernetes в общей инфраструктуре владельца не следует
считать уже подключёнными к этой инстанции Convex.

Проверенные четыре VM суммарно предоставляют 10 видимых vCPU и 19,228 GiB
видимой Linux памяти. **Это не единый вычислительный пул «Сферы»**: ресурсы
распределены по разным машинам, есть другие workloads; backend сейчас имеет
ресурсы только своего узла. Три VPS Fred — не доказательство трёх независимых
зон доступности и не active-active кластер приложения.

Число одновременно обслуживаемых пользователей, устойчивые RPS и p95/p99
**пока не измерены**. Низкая текущая загрузка подтверждает только отсутствие
нагрузки в момент снимка. Whitepaper даёт точные наблюдения, прозрачные
пересчёты и методику получения ёмкости без вымышленных гарантий.

## 3. Непосредственно проверенные VM

GiB = 2³⁰ байт; MiB = 2²⁰ байт. «RAM доступно» — MemAvailable, а не MemFree.
«FS доступно» — Available из df; это не общая ёмкость диска провайдера.

| Termius / узел | vCPU nproc | RAM, GiB | RAM доступно, GiB | Корневая FS, GiB | FS доступно, GiB | Роль по наблюдениям |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Fred Sberov / first | 2 | 3,824 | 2,736 | 29,422 | 18,027 | Nginx Proxy Manager; также maintenance web/Watchtower другого приложения |
| Fred Sberov the 2nd / vm-second | 2 | 3,824 | 3,229 | 29,422 | 21,473 | Работающий Tailscale через snap; Docker не установлен, k3s/k3s-agent не active |
| Fred Sberov the 3ed / zov | 2 | 3,824 | 3,000 | 29,422 | 15,830 | NPM 2.12.3, FRP server; также RustDesk |
| junk | 4 | 7,755 | 4,602 | 127,935 | 63,973 | Convex, dashboard, web, SMS, OTA, connector и Watchtower |

Каждый Fred имеет диск vda 32 212 254 720 байт = 30 GiB; корневая файловая
система меньше. Значения видимой RAM не являются подтверждением оплаченного
тарифа. CPU steal, выделенность ядер, сетевой лимит и IOPS/SLA провайдера не
измерялись. Название VM не устанавливает её физическую зону.

На Fred2 присутствует DMI `OpenStack Nova`. Этого недостаточно для
идентификации провайдера/региона. Отсутствие active k3s units — наблюдение
стандартных служб, не доказательство отсутствия любого ПО в любой форме.

### Пересчёт ресурсов

- vCPU четырёх VM: `2 + 2 + 2 + 4 = 10`.
- RAM: `(4 106 108 928 + 4 106 223 616 + 4 106 231 808 + 8 326 950 912) / 2³⁰ = 19,227634 GiB`.
- Fred-диски: `3 × 30 = 90 GiB` виртуальной блочной ёмкости; это не распределённое хранилище.
- Том Convex: `300 120 KiB / 1024 = 293,085938 MiB` allocated по du.
  Это **весь том**, не размер медицинских данных и не логический размер таблиц.

Ресурсы нельзя складывать с памятью/дисками их гипервизоров как независимые
запасы. Доступная память — снимок, не обещание зарезервированной ёмкости.

## 5. Архитектура и устойчивость

Native-клиенты завершают запись в SQLCipher/outbox до сети. Это защищает
завершённые локальные записи при временной недоступности backend, но не
делает облачные операции доступными. Sync protocol 1 обнаруживает конфликты;
legacy timestamp-клиенты имеют отдельные ограничения совместимости.

| Компонент | Подтверждено сейчас | Не подтверждено / ограничение |
| --- | --- | --- |
| Convex | Один backend, постоянный том, отдельный dashboard | Прикладной failover, реплика backend, восстановление из backup под нагрузкой |
| Public ingress | NPM на Fred1 и Fred3, FRP на Fred3, connector на junk | Автоматическая перебалансировка одного домена между Fred, независимые зоны |
| SMS | Приватный gateway и единственная описанная модемная цепочка | Второй независимый канал и exactly-once внешней доставки |
| Email | Код прямого Resend API, без отдельного email-контейнера | Текущая квота, доставка провайдера и её SLA в этом аудите |
| AI/OCR | Yandex adapter, отдельные согласия/limits/request reservations | Текущие provider квоты и latency, runtime-флаги, нагрузочная ёмкость |
| OTA | Отдельный подписанный protocol/channel/runtime delivery | HA указателей каналов/артефактов; ёмкость массового скачивания |

Исправные health checks и длительный uptime — не гарантия будущей
доступности. Docker restart не заменяет резерв узла. Асинхронная репликация
PostgreSQL допускает ненулевой RPO. Наличие резервной VM не означает
проверенный failback. Отдельная [целевая схема k3s](target-k3s-three-zones.md)
не должна использоваться в презентации как карта развёрнутой «Сферы».

### 6.1. Три отдельных кластера, не три независимые зоны

| K3s-кластер | VM | Выделенные vCPU | RAM VM, GiB | Диски VM, GiB | Control plane |
| --- | ---: | ---: | ---: | ---: | --- |
| dev | 3 | 12 | 48 | 768 | 3 server |
| gitlab | 3 | 12 | 32 | 1 536 | 3 server |
| db-for-k3s | 3 | 12 | 24 | 384 | **1 server + 2 agent** |
| Сумма выделений VM | 9 | **36** | **104** | **2 688** | Три самостоятельных кластера |

Все девять VM находятся на трёх гипервизорах **одной площадки Sasha**.
DevOps сопоставил Node systemUUID и VM SMBIOS, а не только имена/labels:

| Гипервизор | Размещение |
| --- | --- |
| pve | dev-1, gitlab-1, первый DB node |
| pve1 | dev-2, gitlab-2, второй DB node |
| pve2 | dev-3, gitlab-3, третий DB node |

Метки yas/yarik на Kubernetes-узлах не доказывают физические зоны и не
соответствуют независимым площадкам этих VM. Отказ всей Sasha затронет все
три K3s. Девять физических узлов в Proxmox-кластерах Sasha/Yas/Svet online,
каждый Proxmox имеет quorum 3/3, но независимость питания, каналов связи и
ЦОД документально не установлена. Quorum не заменяет независимость зон.

Сумма 36/104/2688 — **выделения виртуальных машин**, не дополнительная физическая
ёмкость и не свободный пул для «Сферы». Диски включают системные тома; это не
полезная ёмкость Longhorn после репликации. Не складывать эти значения с
ресурсами тех же гипервизоров.

### 6.2. Overcommit и запас при отказе

| Гипервизор Sasha | vCPU гостям / аппаратных потоков | Максимальная RAM гостям / RAM ОС | Отношение выделений |
| --- | --- | --- | --- |
| pve | 41 / 16 | 106,75 / 60,61 GiB | CPU 2,563×; RAM около 1,761× |
| pve2 | 30 / 16 | 84 / 60,61 GiB | CPU 1,875×; RAM около 1,386× |

Учитываются соседние нагрузки, не только K3s. Максимальная настроенная RAM
не означает текущее потребление, но и не подтверждает возможность собрать
все VM на оставшихся узлах после отказа. Полного расчёта N−1 по текущим
нагрузкам в сообщениях нет. Proxmox HA-resources и штатные replication/backup
jobs в трёх кластерах не обнаружены по отчёту DevOps.

### 6.4. Backup/PITR — существенная оговорка

У Patroni `archive_mode=on`, но `archive_command=/bin/true`.
**Эта команда не сохраняет WAL.** Успешный счётчик PostgreSQL archiver не
доказывает наличие восстановимого WAL-архива или PITR.

Backup Job dev/prod успешно завершился 13 сентября в 00:01:58 UTC, но
полнота объектов, manifest/checksums и restore не проверены: endpoint
потребовал дополнительную аутентификацию, которую DevOps не обходил.
Longhorn backup targets не настроены, backup metadata пусты. Измеренных
RPO/RTO и подтверждённого протокола restore/PITR/failover/failback именно
«Сферы» в проверенных источниках нет. Резервные копии не объявляются
отсутствующими повсюду — отсутствует доказательство восстановимости.

## 7. Сколько пользователей поддерживается

**Из полученных данных это число определить нельзя.** Для вывода нужны
сценарий использования, распределение интенсивности, p95/p99 и допустимые
ошибки, количество активных WebSocket-подписок, объём истории, ресурсы
backend и квоты внешнего AI. Общее число аккаунтов не равно concurrent users.

### Прозрачная модель нагрузки

Пусть C — одновременно активные пользователи, r — серверные операции на
пользователя в секунду. Тогда `λ = C × r` операций/с. Если каждый делает
одну операцию раз в пять секунд, r = 0,2. Это **пример профиля**, не замер:

| Сценарий | C | Операции/с при r = 0,2 | AI запросы/с при одном на пользователя за 5 минут |
| --- | ---: | ---: | ---: |
| Малый тест | 10 | 2 | 0,0333 |
| Средний тест | 100 | 20 | 0,3333 |
| Большой тест | 1 000 | 200 | 3,3333 |

Таблица задаёт входные нагрузки для будущих тестов, а не обещает их выдержать.
По закону сохранения потока `L ≈ λ × W`: при **предположении** среднего
AI latency 8 с последняя строка означает около 26,7 одновременно ожидающих
AI-запросов. Фактические latency/квоты не измерены. Время внешнего AI не
эквивалентно времени CPU Convex; коэффициент «RAM на пользователя» неизвестен.

Для зарегистрированных пользователей дополнительно нужны доля DAU, доля
одновременной активности и пиковый коэффициент. Обратный пересчёт из CPU
idle в «поддерживаемые аккаунты» технически некорректен.

### Узкие места агента

Для whitepaper агента полезнее измерять не только RPC/s, но и завершённые
полезные сценарии: диалог, проверка плана, OCR страницы, интерпретация
подтверждённого фрагмента. Измерять время первого/полного ответа, долю
валидных ответов, отказ по политике, повторы и стоимость на завершённый
сценарий. Синтетические тесты не доказывают клиническую корректность.

Обязательны отдельные размеры prompt/context, input/output tokens, provider
rate limits, timeout и доля ошибок. Стоимость оценивается как сумма
`input_tokens × input_price + output_tokens × output_price` по реальному
тарифу, плюс VM/storage/traffic. Тарифы в этом аудите не получены, поэтому
рублёвые суммы и стоимость на пользователя не заявляются.

## 8. Как получить доказуемую ёмкость

Следующий этап требует отдельного разрешения на нагрузочный стенд.

1. Развернуть изолированную копию конфигурации с синтетическими данными,
   не копировать медицинскую БД. Запретить реальные SMS/USSD/email.
2. Отдельно измерить Auth без внешней доставки, sync write/read, историю,
   WebSocket reconnect/fan-out и conflicted updates. Зафиксировать размеры
   batch/документов/истории и модель пользователей.
3. Для AI сначала stub-провайдер, затем отдельно согласованные платные
   provider tests с лимитами. Не смешивать CPU capacity и provider capacity.
4. Рампировать нагрузку ступенями, выполнять steady-state и длительный прогон;
   измерять p50/p95/p99, throughput успешных операций, ошибки, outbox backlog,
   CPU steal, RSS, I/O latency, сеть и event loop. Проверить восстановление
   после перегрузки, не только кратковременный peak.
5. Зафиксировать максимальную **устойчивую** ступень, удовлетворяющую заранее
   согласованным SLO, и запас ресурсов. Конкретные SLO/RTO/RPO не назначены
   задним числом; HA-тесты и restore — отдельный набор.

Форма результата: «На commit X, конфигурации Y и профиле нагрузки Z,
при C concurrent clients получены throughput R, p95 T, error rate E за D
минут». До такого отчёта число пользователей маркируется **не измерено**.
